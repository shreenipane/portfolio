Linux resource management

Keeping a server fast next to noisy neighbours

VAGUS

Python 3.14cgroups v2eBPF (C)PyTorchSQLite170+ tests

A monitor → plan → execute loop for Linux servers. It samples every cgroup’s CPU, memory and I/O into SQLite, sizes cpu.max and cpu.weight from observed P95 demand, and writes limits through a crash-safe journal. It previews changes by default, can undo an interrupted apply, and rolls back on its own if the protected service’s pressure stall rate gets worse.

Offline, an LSTM forecasts P95 demand and a Double-DQN places workloads across a simulated cluster. Both are benchmarked against simpler baselines.

258 ms→9.0 ms

The service’s P99 latency under a CPU hog plus a UDP flood, before and after VAGUS’s plan. The service alone runs at 8.4 ms.

How I work

Numbers I can defend

Withdraw what doesn’t hold

When a review I ran found VAGUS’s first benchmark harness starving its own load generator, I withdrew the headline result, re-ran the experiment with an open-loop load and a protected client, and published the raw latencies.

Abstain before guessing

PulseGlass shows no heart rate rather than a noisy one. VAGUS fails closed on missing or stale telemetry and rolls back any change that makes the stall rate worse.

Beat the simple baseline

The LSTM forecaster is compared with ARIMA and a calibrated seasonal-naive model. The naive model came close, and the attention layer did nothing measurable, so the write-up says both.
